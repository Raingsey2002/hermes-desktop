# Skills

Skills are reusable SKILL.md-based capabilities the agent can load — the desktop's Skills screen installs, lists, and removes them, and the [[chat-input]] can invoke one directly.

[[src/renderer/src/screens/Skills/Skills.tsx#Skills]] renders both the standalone Skills nav view ([[src/renderer/src/screens/Layout/Layout.tsx]]) and the embedded pane under Capabilities → Skills ([[src/renderer/src/screens/Tools/Tools.tsx]], `embedded` prop hides the page title and the Browse tab). It shows two tabs — installed skills, and a Browse tab listing the bundled catalog with per-card Install buttons — backed by [[src/main/skills.ts#listInstalledSkills]] and [[src/main/skills.ts#listBundledSkills]].

## Gateway-routed skills, local and remote

Skill list/content operations go through the same gateway HTTP API in local mode that remote mode already used, so skill data comes from one code path regardless of connection mode instead of two independently-maintained ones.

In remote (HTTP) mode the Skills surface must read and mutate the REMOTE machine's skills — the handlers used to fall through to the local CLI, showing (and installing into!) the wrong machine's skills (#578). [[src/main/gateway-skills.ts]] talks to the gateway's `GET /api/skills`, `GET /api/skills/content`, `POST /api/skills/hub/install|uninstall` (web_server.py) via [[src/main/hermes.ts#getApiUrl]] + [[src/main/hermes.ts#getApiAuthHeaders]] — both already resolve to the right endpoint and auth for local, remote, and SSH, since each local profile also runs its gateway as an HTTP server on its own port. `gatewayListInstalledSkills`/`gatewayGetSkillContent` are therefore usable from any mode, not just remote; they throw on failure rather than swallowing to `[]`, so a caller with a fallback (local mode, the CLI) can tell "gateway call failed" apart from "genuinely empty".

The `list-installed-skills` IPC handler ([[src/main/ipc/register.ts#registerIpcHandlers]]) branches: SSH keeps its own tunnel-exec path ([[src/main/ssh-remote.ts#sshListInstalledSkills]], full local access already via the tunnel); remote mode calls the gateway directly; local mode calls [[src/main/hermes.ts#startGatewayWithRecovery]] first and, only if that succeeds, tries the gateway API, falling back to the direct CLI ([[src/main/skills.ts#listInstalledSkills]]) on any failure so a not-yet-started gateway never blocks the Skills screen. `get-skill-content` dispatches on the **path shape** rather than the connection mode: a `gateway-skill:<profile>:<name>` marker path (from [[src/main/gateway-skills.ts#gatewaySkillPath]]) always routes to `gatewayGetSkillContent`, whichever mode listed it; a real filesystem path (a local-mode CLI-fallback listing) reads directly.

Install/uninstall stay on the local CLI path in local mode instead of also routing through the gateway's hub endpoints: those endpoints spawn the CLI server-side and return immediately (`{ok, pid}`) — success means "started", not "completed" — whereas the local CLI path ([[src/main/skills.ts#installSkill]] / [[src/main/skills.ts#uninstallSkill]]) is synchronous and gives a real pass/fail classification via [[src/main/skills.ts#classifySkillCliOutput]]. Local mode keeps the better option available; remote mode has no local CLI to fall back to, so it accepts the async result and the renderer's list refresh picks up the outcome.

Because the Skills UI now works everywhere, [[src/renderer/src/screens/Layout/Layout.tsx]] and [[src/renderer/src/screens/Tools/Tools.tsx]] no longer gate it behind a `RemoteNotice` "not available" placeholder in remote mode — that placeholder used to hide a feature the backend already fully supported.

## Install from a URL, hub identifier, or local file

The Skills screen previously offered only "install from the bundled catalog" or "uninstall" — nothing let a user add a skill of their own, even though the underlying installer already could.

`hermes skills install <identifier>` accepts either a hub identifier or a direct HTTP(S) URL to a SKILL.md — the CLI help text says so, but no field in the UI ever exposed a place to type one that isn't a catalog card. [[src/renderer/src/screens/Skills/Skills.tsx#Skills]] now has an always-visible "add skill" row (`skills-add-row`) with a free-text field wired to the existing `installSkill` IPC (unaffected by mode — it already routes through gateway/SSH/local as appropriate), so a URL or identifier not in the catalog installs the same way a catalog card does.

A picked local file has no such existing path: the CLI accepts only a hub identifier or a URL, never a local filesystem path, so [[src/main/skills.ts#installSkillFromPath]] bypasses the CLI and copies the file (or, if a folder was picked, the whole folder) straight into `<profile>/skills/custom/<slugified-name>/`, reading the skill's name from SKILL.md frontmatter when present. It's reachable only through the `select-skill-file` / `install-skill-from-path` IPC handlers, gated to local mode both in the renderer (the button only renders when `!isRemoteMode()`) and again in the main process (writing would otherwise land in the desktop's own local profile directory while "connected" to a remote/SSH machine, silently missing the intended target). A picked single file is copied alone, not its whole containing folder — copying the folder is reserved for an explicitly-picked folder, so an install can't accidentally pull in unrelated sibling files from wherever the user happened to browse (Downloads, Desktop, …).

## Chat-input skill picker

Skills were previously invocable only by typing `/skill-name` from memory; there was no way to see what's installed without leaving the conversation.

[[src/renderer/src/screens/Chat/SkillPicker.tsx#SkillPicker]] adds a popover trigger to the chat toolbar (next to [[model-selection|the model picker]] and the reasoning-effort control), fetching the installed-skills list on open and rendering a searchable flat list — deliberately no install/uninstall actions here, since that's the Skills screen's job. Picking a skill calls [[src/renderer/src/screens/Chat/Chat.tsx#Chat]]'s `handleSelectSkill`, which sets the composer text to `/<name> ` via the existing `ChatInputHandle.setText` — the pick doesn't invoke anything itself, it fills in what the user would have typed, so the message still goes through the same slash-command → skill execution path ([[chat-commands#Slash command execution]], `slashExec.ts`'s `case "skill"`) as if typed by hand.
